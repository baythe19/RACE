## What is actually good (verified, not assumed)

- **Repository-wide auth is on by default.** `vendorRoutes.ts:31`, `driverRoutes.ts:24`, `towingBookingRoutes.ts:16`, `driverBookingRoutes.ts:16`, `bookingRoutes.ts:10`, `paymentRoutes.ts:10`, `bookingPaymentRoutes.ts:13`, `locationRoutes.ts:10`, `notificationRoutes.ts:10`, `profileRoutes.ts:10` all `router.use(authMiddleware)` at the top. Every admin router file I read (`vendorsRoutes`, `bookingsRoutes`, `driversRoutes`, `customersRoutes`, `financeRoutes`, `settingsRoutes`, `reportsRoutes`, `notificationsRoutes`, `adminsRoutes`, `subscriptionsRoutes`, `documentsRoutes`, `adminDashboardRoutes`) puts `adminAuthMiddleware` **and** a `requireAdminPermission(...)` on every route. I found **no** reachable-without-token write endpoint (only `/health`, `/brand`, `/services`, `/fare/*`, `/subscriptions/plans`, `/sos/config`, `POST /auth/*`, and the QR verify by design).
- **`requireRole` re-reads the DB on every request** (`role.ts:14`) and rejects `SUSPENDED`/`INACTIVE` (`role.ts:16`) — so a revoked role or suspension takes effect before the access token expires. This is the right call and is why per-request DB cost is high (see P2).
- **User↔admin token confusion is explicitly blocked.** Same secret, but `utils/src/jwt.ts:63` rejects `tokenType: 'admin'` on user routes and `adminJwt.ts:59` rejects non-admin tokens on admin routes.
- **Booking race hardening on the main paths is real.** Driver reservation is a single conditional `findOneAndUpdate` with `activeBookingId: null`, `isAvailable: true`, vendor match and status exclusions (`driverAssignment.ts:57-86`); offer claiming and assignment both re-check `status: 'CONFIRMED'` + `driverId` null in the update filter (`driverAssignment.ts:760-795`, `946-969`); fleet-vehicle pinning is a conditional update plus an open-job pre-check (`driverAssignment.ts:106-145`); status transitions use compare-and-set on `booking.status` (`towingBookingRepository.ts:54-64`) and cancellation CASes on `status + advancePaid + advanceAmount` (`towingBooking.ts:334-361`); payment writes CAS on `{advancePaid: {$ne:true}}` and roll a losing transaction to `failed` (`bookingPayment.ts:415-431, 145-151`). The vendor/outsider-claim and double-vehicle-pin cases are actually exercised by `verify-driver-ack-e2e.ts` checks 2/3/5/6/7.
- **`assertActorMayTransition`** (`bookingStatusConstants.ts:87-131`) genuinely stops customers from confirming/starting/completing via the generic status PATCH, which is the exploit that usually exists in this kind of app.
- **KYC files are no longer served from an open static route** (`app.ts:38-40`); access goes through `documentRoutes.ts` with an owner/vendor/admin check. Multer has MIME + 10 MB limits (`upload.ts:5-16`).
- **OTP replay hardening (VOC P0.8)** is genuinely fixed for re-verify (`authRepository.ts:55-65`), Hanu OTPs are stored as `sha256(otp+pepper)` (`otp.ts:31-34`), and the Hanu key is not logged (only `res.status` + 300 chars of body, `hanuSms.ts:75-80`).
- **Offer routing avoids cross-tenant leakage on the main feed**: `VENDOR_MANAGED` drivers get zero marketplace offers (`driverAssignment.ts:379-381`), independent drivers only get driver-hire jobs (`selectOpenOfferBookingTypes`, :355-366), vendor-linked drivers only see their own vendor's jobs (:446-449 and :489-493). Socket rooms are authorized server-side from the principal (`socket.ts:64-99`) and the handshake requires a valid user token (`socket.ts:27-52`).
- CSS/HTML escaping in the public QR page is correct (`vehicleVerifyPage.ts:170`), and path traversal on local document reads is blocked (`documentRoutes.ts:81`).

## P0 — fix before any real customer traffic

### P0-1. Customer-only trip OTP / completion OTP are leaked to the customer API *and* the booking room *and* the driver
- `bookings/towingBooking.ts:59-60` and `bookings/driverBooking.ts:63-64` put `tripStartOtp` and `completionOtp` into every response, including `createBooking` → so **immediately after booking creation** the customer already knows the completion OTP.
- The same mappers are used for the customer list (`towingBooking.ts:137-143`, `driverBooking.ts:145-150`).
- `driver.ts:518-527` emits `completionOtp` to the driver when the driver taps "arrived at dropoff"; `combinedBooking.ts:174-181` emits `completionOtp` to the whole `booking:<id>` room (customer, driver, vendor, admin viewers).
- `customerTripOtp()` only hides the code in a narrow status window (`tripOtp.ts:38-46`); `customerCompletionOtp()` returns it from `CONFIRMED` onward (`tripOtp.ts:80-94`).
- **Risk:** the entire point of the code is "the customer reads a code to the partner". A customer who cancels, a driver who was assigned and rejected, or a vendor with room access can replay them. More practically: the customer can hand the completion code to the driver by message while never paying, and `paymentConfirmedByCustomer` is not a gate on `COMPLETED` (see P1-3).
- **Fix:** never return either OTP in any DTO. Gate trip-start on the customer receiving it only while `DRIVER_EN_ROUTE|DRIVER_ARRIVED`, and completion on `arrivedAtDropoffAt && paymentConfirmedByCustomer`. Emit to `driver:<id>` only, never to `booking:<id>`. Store OTPs hashed (`tripOtp.ts` already has the `MAX_TRIP_OTP_ATTEMPTS` machinery; hash comparison is a 3-line change).

### P0-2. `start-otp` bug is real: a **2-digit code** kills the 4-digit regex, so "not ready" and "invalid format" are indistinguishable
- `handler` bug in `utils/src/otp.ts:3-5`: `crypto.randomInt(100000, 999999)` is correct — but `generateTripStartOtp` (`tripOtp.ts:8`) and `generateCompletionOtp` (`tripOtp.ts:50`) use `String(randomInt(1000, 10000))` which yields `1000..9999`, always 4 digits. So the *generation* is fine. The real defect is the **validator allows `undefined`**. `driverValidator.ts:23-27` declares `tripOtp: z.string().regex(/^\d{4}$/).optional()` and `completionOtp` likewise; `driver.ts:349` only calls `assertCompletionOtp` if `booking.completionOtp || booking.arrivedAtDropoffAt`. A booking that reached `IN_PROGRESS` and then `COMPLETED` without either field set skips completion OTP entirely. `verify-dropoff...` shows the happy path guarded, but the fallback path is unguarded.
- **Risk:** a driver can complete without customer payment confirmation whenever `arrivedAtDropoffAt` and `completionOtp` are both unset — e.g. after a Mongo restore, or if a booking was created by seed / admin / migration.
- **Fix:** make `completionOtp` mandatory for `COMPLETED` in the schema and always call `assertCompletionOtp`; make `tripOtp` mandatory for `IN_PROGRESS`. There is no legitimate "OTP not set so allow it" state once a trip started.

### P0-3. `MOCK_DATA_MODE` defaults to `true` and still mints universal-OTP sessions as long as the env var is literally "true"
- `config/env.ts:39-42` → `MOCK_DATA_MODE` defaults to `'true'`. `productionGuard.ts:22-24` only fails if `env.MOCK_DATA_MODE` is true, which reads as safe — but `productionGuard.ts:16` returns early whenever `NODE_ENV !== 'production'`, and `otp.ts:250-252` treats `MOCK_DATA_MODE || NODE_ENV !== 'production'` as "accept 123456". So any deploy that forgets `NODE_ENV=production` (very common with `PM2` + `dotenv` overrides) runs with:
  - universal OTP `123456` accepted for every account (`otp.ts:250-252`),
  - `devOtp` returned in the body (`otp.ts:157-159`),
  - `assertResendAllowed` disabled (`otp.ts:61-63`),
  - driver self-registration auto-APPROVED (`driverSelf.ts:54`),
  - vendor driver creation auto-APPROVED (`vendorDrivers.ts:346-350`),
  - vendor document requirement waived (`vendor.ts:307-313`).
  I verified `deploy/ecosystem.config.cjs:17` sets `NODE_ENV: 'production'` and `backend/.env.example` sets `NODE_ENV=development`, so the shipped deploy is correct — the risk is any manual `node dist/index.js` or Docker run without the PM2 wrapper.
- **Fix:** default `MOCK_DATA_MODE` to `false`; in `productionGuard`, also fail when `NODE_ENV` is unset/`development` *and* `process.env.PORT` looks like production, or (simpler and safer) make `devOtp`/auto-approve require an explicit `ALLOW_DEV_CONVENIENCES=true`. The current guard is good; it just doesn't cover "NODE_ENV wrong".
- **Filing update (2026-10-26):** `config/env.ts` now defaults `MOCK_DATA_MODE` to `false`. `ALLOW_DEV_CONVENIENCES` gate not implemented in this pass.

### P0-4. `OTP_PEPPER` unset silently falls back to the OTP provider token as the pepper
- `services/src/otp.ts:32-34`: `env.OTP_PEPPER ?? \`race-otp::${env.MC_AUTH_TOKEN ?? 'local-dev'}\``. If MessageCentral is retired (`MC_AUTH_TOKEN` removed) every Hanu OTP hash now uses the **public constant** `race-otp::local-dev`, so an attacker with a read-only DB dump can precompute the 900k-code space trivially. `productionGuard.ts:31-37` never checks `OTP_PEPPER`.
- **Risk:** leaked `OtpLog` collection → offline brute force → still valid OTPs if the attacker can race the 5-minute window. This is low-likelihood without a DB leak, but the guard is free to add.
- **Fix:** `productionGuard` should require `OTP_PEPPER` (≥32 chars) whenever Hanu is configured; remove the `local-dev` constant.
- **Filing update (2026-10-26):** `productionGuard.ts` now fails boot in production when `HANU_API_KEY` is set and `OTP_PEPPER` is missing or shorter than 32 chars. Pepper fallback in `services/src/otp.ts` unchanged.

### P0-5. Admin-created driver "without login" gets the global `DRIVERS_MANAGE` path into any vendor fleet — and can be used to claim a phone number
- `adminDrivers.ts:143-162` `create` accepts `input.vendorId` and writes `driverProfile.vendorUserId` with `fleetSource` unset (so *not* `admin`), but it does **not** create a `DriverVendorMembership`, does not check whether the phone is already an existing user (`UserModel.create` will throw on the unique mobile index — acceptable), and does not require `DRIVERS_MANAGE` to know the vendor. `adminVendors.ts:734-748` `unassignDriver` only removes admin-assigned (`fleetSource === 'admin'`) drivers, so drivers created here **cannot be unassigned** through the admin UI. Meanwhile `claimOpenBookingOffer:665-687` treats `bookingVendorId` as authorization and requires `DriverVendorMembership`, so these admin-created drivers can never claim their vendor's jobs — but they *do* appear in `vendorDriversService.list` (`vendorDrivers.ts:89-95`), get counted as fleet (`assertVendorApproved` reads the vendor), and show up in the vendor's `listBookings` driver-id set (`vendorBookings.ts:156-169`).
- **Risk:** an admin (or a compromised admin token) can attach an arbitrary existing driver to a vendor, and the vendor then sees that driver's bookings/fleet data. The reverse (removing) is impossible. This is a real cross-tenant visibility hole gated only by an admin role.
- **Fix:** reject `vendorId` in `adminDrivers.create` unless it also creates an ACTIVE membership, or route it through `vendorDriversService.createStaffDriver` / `claimByPhone` so the membership invariant holds. Add `fleetSource: 'admin'` if admin-assigned.

### P0-6. Booking payment verification is client-asserted — a customer can mark their own booking paid
- `bookingPaymentValidator.ts:10-13` accepts `status: z.enum(PAYMENT_TRANSACTION_STATUSES)`; `bookingPayment.ts:228` → `setPaymentTransactionStatus(transaction.id, customerId, 'advance', 'success')` trusts it. This is currently **mitigated by `assertStubPaymentsEnabled()`** (`bookingPayment.ts:41-48`), which 503s in production unless `ALLOW_STUB_PAYMENTS=true`. So today prod is safe. But the guard is a single env var, and the check is not logged at startup.
- **Risk:** anyone who flips `ALLOW_STUB_PAYMENTS=true` (it's documented in the error string, so someone will) turns `/payments/advance/verify` into a free "confirm booking" button.
- **Fix:** add `ALLOW_STUB_PAYMENTS` to `productionGuard`'s fatal list *and* rename it `ALLOW_STUB_PAYMENTS_SANDBOX_ONLY`, requiring `NODE_ENV !== 'production'`. When the real gateway lands, `verify` must verify a signature server-side.

## P1 — correctness / security with real blast radius

### P1-1. Cancel races with vendor assignment → orphaned fleet-vehicle lock and a busy driver
- `towingBooking.ts:354-361`: cancellation CASes only on `{status, advancePaid, advanceAmount}`. It does **not** check `driverId`/`vendorId`. Between the `findById` at :306 and the CAS, `claimOpenBookingOffer` can legally set `driverId + status: DRIVER_ASSIGNED` (its filter requires `status: CONFIRMED`, and the cancel CAS only requires `status === booking.status`, which is still `CONFIRMED` at that instant, so both wins are possible depending on ordering). Then `releaseDriver(booking.driverId...)` frees the driver — but `releaseFleetVehicleFromBooking(booking._id)` frees the *vehicle*, and the driver is already free, so the net state is consistent *if both writes land*.
  The real leak is the inverse ordering in `claimOpenBookingOffer:768-798`: `reserveDriver` → `reserveFleetVehicle` → `booking CAS`. If the booking CAS fails (cancel won), it does `releaseDriver(driverId, bookingId)` and `releaseFleetVehicleFromBooking(bookingId)` — correct. **But** `releaseDriver` (`driverAssignment.ts:974-990`) only clears the driver if `activeBookingId` still equals *this* booking. If the driver was re-reserved by a *second* claim in between (two vendors dispatching the same driver is prevented by the driver filter, so this is narrow), the rollback silently no-ops and leaves `isAvailable: false`. Documented, not fixed.
- **Risk:** a `DRIVER_EN_ROUTE` fleet vehicle can stay pinned to a `CANCELLED` booking if the process dies between the CAS and `releaseFleetVehicleFromBooking` (:368). Nothing ever reconciles it. That vehicle then returns `ConflictError: This fleet vehicle is already on another open job` for every future dispatch (`driverAssignment.ts:105-113`), permanently until a human clears `activeBookingId`.
- **Fix:** make cancellation a single atomic update that also `$unset`s the vehicle, or run a boot-time reconciliation (`VendorVehicleModel.updateMany({activeBookingId: {$in: cancelledIds}}, {$set:{activeBookingId:null}})`); add `driverId` to the cancel filter and fail if a driver was assigned in the meantime.

### P1-2. Admin/auto-assign never pins the fleet vehicle to the driver's own booking → the driver's truck can be dispatched twice
- `adminServiceBookings.ts:19-68` / `driverAssignment.ts:886-973` call `assignDriverToBooking`, which reserves the **driver** (`reserveDriverForBooking`) but never calls `reserveFleetVehicleForBooking`. The vendor path (`vendorBookings.assignBooking:317-321`) passes `fleetVehicleId`, so it does pin. Then `reserveFleetVehicleForBooking:106-113`'s `openJobFilter` looks for `assignedFleetVehicleId: vehicleId, status in open statuses` — a booking assigned via admin has **no** `assignedFleetVehicleId` field, so the truck the admin driver is driving shows as free.
- **Risk:** vendor A's truck T is on admin-assigned job J1 (driver D1 = the truck's usual driver). Vendor B approves job J2 and picks truck T. `openJobFilter` finds no clash (J1 has no `assignedFleetVehicleId`), `VendorVehicleModel` has no `activeBookingId` for J1 (admin path never set it), so T is pinned to J2. Two jobs, one truck. Also `assertVehicleHasNoOpenAssignments` (`vendorVehicles.ts:63-80`) won't block deleting T.
- **Fix:** `assignDriverToBooking` should derive the driver's `driverProfile.vehicleRegistration`, look up the vendor vehicle, and go through `reserveFleetVehicleForBooking` + set `assignedFleetVehicleId/Label`.

### P1-3. `paymentConfirmedByCustomer` is never required before `COMPLETED`
- `driver.ts:349-361`: completion OTP is checked, but `paymentConfirmedByCustomer` (`combinedBooking.ts:139-142`) is not. The completion OTP is generated at `combinedBooking.ts:135` when the customer confirms the payment mode, and generated independently at `driver.ts:500`. So the two OTPs can differ (see P2-6).
- **Risk:** customer never opens the payment-mode screen, driver taps "arrived at dropoff", gets a *different* OTP from `driver.ts:500`, customer reads the code from their **booking list** (`towingBooking.ts:60` sends it regardless of status), driver completes. Cash never collected — the cash collection is purely out-of-band so the "stub payments" model is not the issue here; the state machine just claims it was collected.
- **Fix:** gate `COMPLETED` on `paymentConfirmedByCustomer === true` and one canonical OTP (only `combinedBooking.confirmPaymentMode` should generate it).

### P1-4. `vendorVehicle.status !== 'ACTIVE'` traps the booking — driver can never accept, vendor can never approve again
- `driverAssignment.ts:693-707`: on claim of a vendor-routed booking, if `assignedFleetVehicleId` is set and the vehicle is no longer `ACTIVE`, it throws `ConflictError`. But `vendorVehicles.update:144-146` only blocks moving *away* from `ACTIVE` when there is an open job (`assertVehicleHasNoOpenAssignments:63-80`) — and `PUT /vendor/vehicles/:id` accepts any status from `vendorValidator.updateVendorVehicleSchema`, so a vendor can send `INACTIVE` and the guard runs `TowingBookingModel.exists({assignedFleetVehicleId, status in [...]})`. The vehicle *was* pinned before the booking reached `DRIVER_ASSIGNED`, so this guard passes only if `assignedFleetVehicleId` is set on the booking. For a booking where the vendor approved (`approveVendorBookingOffer:568-570` sets `assignedFleetVehicleId`) the guard does see it — good. **But** the admin/payment path can create the booking with `assignedFleetVehicleId` already unset. Then the vehicle goes `INACTIVE`, and the claim permanently fails with a 409 that instructs "ask your vendor to review the assignment" — but `vendorBookingsService.assignBooking` requires `status === 'CONFIRMED'` and `driverId` null on the booking filter (:760-763); after the failed claim, it's still that state, so a re-assign works only for towing with a vehicle; for driver-hire with `vehicleId` omitted the vehicle is not re-pinned.
- **Risk:** supported in `verify-driver-ack` only for the happy path. Real failure path: stuck `DRIVER_ASSIGNED` for an hour, customer cancels at 50% refund (`cancellation.ts:36-44`).
- **Fix:** allow the driver accept (or the vendor re-approve) to swap/clear the fleet vehicle when it is no longer ACTIVE, instead of hard-blocking.

### P1-5. Driver OTP attempt counters are incremented non-atomically and never reset on trip start for the vendor path
- `driver.ts:338-345` / `vendorBookings.ts:360-368`: on a wrong code they do a separate `$inc`. `assertTripStartOtp` reads the in-memory doc. Two parallel wrong attempts both read `attempts: 4` and both `$inc` → `6`, which just locks earlier (benign). Two parallel *correct* attempts both read `attempts: 0` and both succeed → the trip-start transition has a CAS (`tripStartOtpVerified: {$ne: true}` in `driver.ts:388-398`) but the **vendor** path (`vendorBookings.ts:371-378`) also CASes. OK on the success side.
- The real defect: `vendorBookings.verifyTripOtp:360-368` increments `tripStartOtpAttempts` even when `assertTripStartOtp` failed because the OTP *is not ready* ("Wait for partner assignment") or *already verified* — those are not wrong guesses but they burn the 5-attempt budget (`tripOtp.ts:19-24`). Same in `driver.ts:338-345` for `dto.status === 'IN_PROGRESS'` when `tripStartOtp` is missing.
- **Fix:** only `$inc` when the failure is `booking.tripStartOtp !== code`; return early for "not ready"/"already verified".

### P1-6. `refreshToken` silently switches the active surface when the stored capability is gone
- `auth.ts:289-297`: `activeRole = payload.role && hasUserCapability(user, payload.role) ? payload.role : user.role`. If the driver capability is removed (vendor onboarding flow unsets `passwordHash` etc. but `capabilities` may still contain driver), the refresh silently downgrades. More importantly, `refreshToken` does **not** re-check `canAddUserCapability` or role-mismatch, and it lets a `VENDOR_MANAGED` driver keep a driver token after `driverProfile.vendorUserId` was unset.
- **Risk:** a vendor-managed driver whose membership was revoked (`driverVendorMembership.revoke:349-359` unsets `loginId`/`passwordHash` on the profile but leaves `refresh:*` keys) can keep refreshing for 7 days (`JWT_REFRESH_EXPIRES_IN` default) with a driver token; `requireRole('driver')` still passes because it only checks `hasUserCapability`.
- **Fix:** on revoke/remove, call a shared `revokeAllUserRefreshTokens(userId)`; in `refreshToken` reject when `activeRole` no longer matches the requested role instead of silently switching.

### P1-7. Vendor `uploadDocument` / `update` are role-less and let a **customer** become a vendor document holder
- `vendorRoutes.ts:33-37`: `/draft`, `/register`, `/update`, `/profile`, `/status`, `/upload-document`, `/selfie` only have `authMiddleware`, no `requireRole('vendor')`. `vendorService.uploadDocument:216-218` calls `vendorRepository.findByUserId(userId)` which also matches any user with `vendorProfile: { $exists: true }` (`vendorRepository.ts:68-73`) — but a customer with no vendorProfile gets `404`, so exploit is narrow. However `register` (`vendor.ts:247-318`) sets `user.role = 'vendor'` on any authenticated customer, `saveDraft` creates a vendorProfile, and `vendorRepository.create({userId})` **overwrites** `user.role = 'vendor'` (`vendorRepository.ts:48`).
- **Risk:** a customer (whose account may also have driver capability) can escalate to vendor by calling `POST /api/v1/vendor/register`. `canAddUserCapability` (`roles.ts:23-28`) explicitly forbids adding vendor to customer/driver accounts — but this path bypasses it. After that, `requireRole('vendor')` passes (`role.ts:17` picks up `dbUser` capability). The account still has provider bank details path open (`/vendor/payout-account`).
- **Fix:** in `vendorService.register`/`saveDraft`, reject when `!user.isVerified` or when `getUserCapabilities(user)` contains `driver` (mirroring `canAddUserCapability`); or add `requireRole` guards and an explicit "become vendor" capability check.

### P1-8. `vendor → driver` and `driver → vendor` dual capability is not enforced anywhere else
- `roles.ts:21-28` states vendor is a "separate account mode". Yet `auth.ts:69-79` `assertRoleAccess` returns early for unverified users, and `ensureUserRole:117-122` will *switch* `user.role` to the requested role without rejecting a vendor account that requests driver. Combined with P1-7 that gives an arbitrary person `vendor + driver` — and `driverAssignment.ts:665-687` uses only membership for dispatch, while `vendorBookings.assertVendorApproved` uses role. A member can therefore hold both sides of a job (claim own vendor's job as driver).
- **Fix:** reject capability adds that would produce `{vendor, driver}` anywhere the capability is written (`auth.ts:186-188`, `driverSelf.ts:49-52`, `vendor.ts:293-300`).

### P1-9. Vehicle QR endpoint leaks full owner PII to anyone with the URL, and `vehicleId` is an ObjectId (not a secret)
- `vehicle.ts:104-127` returns `ownerMobile` and `emergencyMobile` in JSON (`sendSuccess(res, result)`) for `GET /api/v1/vehicles/:id/verify` and `GET /api/v1/qr/:id`. Both are limited by `qrRateLimiter` (20/h per **IP** in prod) but the **only** gate is an unguessable 24-hex id that appears in the URL embedded in every sticker — anyone who photographs a windshield (or a screenshot of the customer's QR screen) has it. There is **no** scan-count / abuse signal check and no owner opt-out.
- **Risk:** personal phone numbers of vehicle owners and their emergency contacts, harvestable at 20/IP/h — with proxies that's an arbitrary PII scrape. `getQrMetadata` is admin-gated (good), but the raw leak already exists.
- **Fix:** return a masked number + a server-side `tel:` proxy (like `sos`), or require a scan token/captcha; at minimum, drop `emergencyMobile` from the JSON variant (keep it in the HTML page which is what a stranger needs).

### P1-10. `documents` proxy will fetch **any** URL a vendor/driver uploaded (SSRF / open proxy against internal network)
- `documentRoutes.ts:90-94`: `await fetch(url)` after ownership check. The document's `url` comes from `storageService` (a GCS URL) *or* from a client-supplied string. `vendorValidator.documentSchema.fileUrl` is `z.string().url()` (`vendorValidator.ts:75-79`) and `registerVendorSchema` accepts `documents[]` with arbitrary `fileUrl`; `driverSelf.register` accepts `documents[].url: z.string()` with **no URL validation at all** (`driverSelf.ts:31-38`).
- **Risk:** an authenticated user stores `fileUrl: http://10.0.0.5:9200/_cluster/health` in their driver document and then requests `/api/v1/documents?url=http://10.0.0.5:9200/...&ownerId=<self>`. The server fetches it and streams the body back. Blind SSRF with response body returned — reads internal metadata (GCP metadata server `http://metadata.google.internal/…`), attacks internal admin ports, and can hit `file://`-style edge cases depending on undici.
- **Fix:** drop the arbitrary-URL branch entirely; store a storage key, not a URL, and only stream from GCS/local. If a URL must be supported, allow-list the bucket hostname.

### P1-11. `driverSelf.register` lets the client pre-set document verification status
- `driverSelf.ts:31-38`: `documents: [{ type, url, status: z.enum(['PENDING','VERIFIED','REJECTED']) }]`. `register:57-62` copies `status` straight into `driverProfile.documents`. Then `adminDrivers.update:179-189` requires "a verified required document" to approve — which the client can self-declare. In non-production `status` is also auto-`APPROVED` (`driverSelf.ts:54`).
- **Risk:** KYC bypass in prod (if `NODE_ENV` wrong — see P0-3) and admin-review confusion in any env: the admin UI will show a green "VERIFIED" doc that was never reviewed.
- **Fix:** force `status: 'PENDING'` server side; also `url` should be the storage key returned by `/driver/upload-document`, not a client URL.

- `comprehensive-audit.ts` — 40-ish **smoke** calls. It asserts almost nothing: `record('Admin', 'GET /admin/dashboard', dashRes.ok, …)` asserts only HTTP 200 and that some key exists.
